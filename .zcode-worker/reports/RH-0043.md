# RH-0043 — Household profile switch and cached-state isolation — verification report

**STATUS: REVIEW** (worker-reported; only the owner accepts and merges)

## Objective met

Profile switching is now protected from stale cached state on the accepted
carrier UI. The household profile is a **live URL identity**: the app tracks
`?profile=<slug>` reactively (Next's router syncs `useSearchParams` with
history navigation and native `history.pushState`/`replaceState`), so an
in-session switch is honored instead of silently serving the previous
profile under the new URL. A switch is a bounded session teardown — in-flight
work is aborted and generation-invalidated, every profile-scoped cached view
(feed, search results and filters, detail modal, spoiler reveals, focus) is
dropped — and every request is identity-bound, so one profile's state cannot
render in another's view. Proven with disposable profile/session fixtures
(two household profiles with disjoint watch state) driving the built app in
a real browser, including deterministic late-response races.

## Visible before → after

| Behavior | Before (main `3f78a8e`) | After (this branch) |
|---|---|---|
| In-session profile switch (history navigation / `pushState`, e.g. remote back/forward between `?profile=` URLs) | Ignored: slug frozen at mount; profile A's feed, search, detail and preferences kept rendering under profile B's URL | Honored: session re-boots for the new identity; nothing scoped to the old identity survives to render |
| Late detail response | Overwrote whichever modal was open, or re-opened a closed modal with stale content | Dropped: request token + abort + generation check; closing the modal or opening another title invalidates the in-flight reply |
| Load more | No guard: double-click appended duplicate/out-of-order pages; late replies after leaving search still wrote state | Single-flight + generation-bound + append-only-onto-the-exact-page-extended |
| Boot fetches | `cancelled` flag guarded setState but fetches were never aborted | Aborted per effect run; aborted generations never land in state |
| Spoiler-shield preference storage | Keyed by mutable display name (RH-0044 format): a rename orphaned the preference; display names were cache keys | Keyed by the contractual slug (feed-resolved, else URL slug, else "demo"); legacy display-name entries migrate once onto the slug and the legacy key is removed |
| Malformed slug in URL | (Same) | Passes through untouched — the server's 404/400 stays the fail-closed identity authority; the client never falls back to another profile |

The server surface needed no change: RH-0044's accepted plumbing already
scopes `/api/home`, `/api/catalog/search`, `/api/catalog/items/:id` by
`?profile=` and fails closed (unknown slug = 404, unscoped = no watch flag).
All changes are client-side plus pure helpers.

## Known limits

- There is no in-app profile switcher and no logout concept in the product;
  identity remains URL-driven. The in-session switch contract is exercised
  through the exact mechanism a future switcher would call
  (`history.pushState` / history navigation), which the router surfaces to
  `useSearchParams`.
- `useSearchParams` moves the `/` shell under a Suspense boundary: the
  prerendered HTML is a minimal skeleton until hydration. API routes are
  unaffected (`force-dynamic`).
- A bfcache restore of a previous document restores that document's own
  (URL-consistent) heap; that is browser-managed and same-profile by
  construction.
- The load-more race check uses synthetic search pages (the fixture catalog
  has 8 items, so no real second page exists); the guard itself is
  production code exercised through the real component.
