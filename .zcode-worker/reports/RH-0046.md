## Objective met

A living-room user can now switch household profiles in-app. The profile pill in the top bar is a real switcher invoker (remote/keyboard focus and pointer parity) that opens a `role="dialog"` roster of the household's ACTIVE profiles with the current session's entry marked Active. Activating a different entry navigates to `/?profile=<slug>` via native `history.pushState` — the exact mechanism the RH-0043 acceptance verified — so the **delivered** RH-0043 identity contract performs the session re-boot (generation invalidation, request aborts, cached-view drops). The switcher never hand-clears caches, generations, or reveal state; it only navigates.

## Roster-source design decision and rationale

**Chosen: a new `GET /api/profiles` route** over extending `/api/home`. Rationale, recorded per spec:

1. **Identity independence:** the switcher must open even when the current session's identity is unresolved (unknown/ghost slug → `/api/home` 404s the whole payload). A roster piggybacked on the feed payload could not load there; the dedicated endpoint has no session identity at all.
2. **Scope honesty:** the roster is household-scoped; `/api/home` is a resolved profile's feed. Mixing an unscoped census into a profile-scoped payload grows a hot payload with data the feed render never uses.
3. **Reuse over invention:** the read already existed — `listProfiles()` in `home-feed.ts` was exported but served by no route. The route is a thin mapper over it (plus payload shaping that strips the internal DB id; the client-side contract exposes only slug/display name/initials/default flag, never emails, account links, or credentials), now with the spec's bounded row cap (`MAX_PROFILE_ROSTER = 50`, active-only, default-first then slug order).

Fail-closed discipline: database unavailable → redacted 503 envelope → honest in-dialog retry state with the session underneath fully usable; empty household → `{profiles:[]}` → honest empty state, never fabricated profiles; identity-less payload rows are dropped client-side and never rendered switchable.

## Known limits

- The roster read is bounded at 50 active profiles by design; a household beyond that would silently truncate (the schema/import make this implausible; the honest cap beats an unbounded read).
- The switcher navigates the app's root URL (`/?profile=<slug>`); deep-link paths beyond `/` are not part of the delivered app surface (the app has exactly one page).
- `initials` rides along in the roster payload (as it already does in `/api/home`'s resolved profile) for avatar rendering; it is display copy derived from the manifest, not additional PII.
- Real TV devices were not exercised (no hardware gate in this environment); keyboard/pointer/reduced-motion verification is browser-based per the delivered accessibility contract.
